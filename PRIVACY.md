# Privacy

One page, because there is one thing to say.

**The image published at `ghcr.io/easybytehub/hullwork` reports Hullwork's own crashes to us. Nothing
else leaves, and nothing of yours can.**

## What is sent

A crash inside Hullwork produces one object of about 350 bytes. This is the whole of it — nine fields,
and there is no tenth:

```json
{
  "schema": 1,
  "exception": "ManifestError",
  "frames": [{"module": "hullwork.manifest", "function": "parse_manifest", "lineno": 707}],
  "release": "0.1.0a8",
  "python": "3.12.13",
  "platform": "linux",
  "operation": "receiver",
  "installation": "cedecf4d048c0d244af84cfa598926c4",
  "counts": {"projects": 3, "items": 41, "attempts": 7, "outcomes": 5}
}
```

Print the one your instance would send:

```
hullwork config --telemetry
```

That command reads your real state and builds a real payload. It writes nothing: asking what would be
sent does not create an installation identifier, because being counted for the act of checking would
be the wrong way round.

## What is not sent, and why it cannot be

| not sent | |
|---|---|
| the error message | the field does not exist in the payload |
| local variables | never read from the event |
| URLs, including your webhook tokens | no field for them |
| your hostname, your machine, your user | nothing is read from the operating system beyond `linux`/`darwin` and the Python version |
| your repository names, project names, item titles | no field for them |
| anything from the errors *your* software reports | Hullwork holds those, and none of them is read |
| your installed packages | the SDK sends this by default; we build the payload ourselves and do not |

**The mechanism matters more than the list.** The payload is not an error report with the sensitive
parts removed — a filter is a blacklist, and blacklists leak. It is **constructed** from an enumerated
set of fields, so a field nobody wrote down cannot appear, including one added by a future version of
some library. The code is [`hullwork/upstream.py`](hullwork/upstream.py); it is short, and it is the
whole of it. The tests beside it try to get a stranger's data through and fail on purpose.

## The installation identifier

Sixteen random bytes, generated by your instance, stored in one row of your database, written the first
time something is actually reported. It is **not** derived from your hostname, your MAC address, your
licence, or a hash of any of them — a hash of a hostname is still the hostname to anybody holding a
list of hostnames to try.

All it does is tell forty crashes from one installation apart from one crash from forty installations.
Those two situations call for opposite work, and without the identifier they are the same forty
events.

Delete the row and you are a new installation. Nothing checks it, nothing expires because of it.

## Why we ask for this at all

A self-hosted tool is invisible to the people who wrote it. A defect that only appears on Postgres, or
on arm64, or on the eleventh project registered, is one we will never see and never fix.

The first release had exactly that shape. `0.1.0a1` shipped without two optional dependencies, so
setting `HULLWORK_ERROR_DSN` made the container exit 3 and a Postgres URL died in a raw traceback —
two capabilities the documentation promised in three places each, impossible in the artefact. Nobody
noticed for a day, because a development checkout installs both and every test passed.

We would rather hear about the next one.

## How to stop it

```
HULLWORK_TELEMETRY=off
```

In `deploy.env`, in your compose file, in the environment — anywhere the process reads. Nothing else
changes; the rest of Hullwork does not care.

**Or build your own image**, which has no destination in it:

```
docker build -t hullwork:mine .
```

The destination is baked into the published image by the release workflow, from a repository secret.
It exists nowhere in this source tree, and
[`test_no_destination_is_hidden_in_the_source_tree`](tests/test_where_a_build_reports_to.py) reads
every tracked file on every commit to keep that true. So this is a property of the repository you can
check, rather than a promise you have to accept.

Your own tracker is unaffected either way: `HULLWORK_ERROR_DSN` sends Hullwork's crashes to **you**,
with the whole event and its secrets scrubbed, and neither of the two destinations silences the other.

## What happens to it

* Sent to **`errors.easybyte.es`**, which is the only address involved and the only thing we expose
  to the internet: a small relay that checks the payload's shape again on arrival and forwards it
  inward. The tracker itself has no public address at all.
* Stored in an error tracker we run, in the EU.
* **Kept for 90 days**, then deleted.
* Read by the two people who work on Hullwork, to fix Hullwork.
* Never sold, never shared, never used to contact anybody — there is nothing in it that could be used
  to contact anybody.

## Questions, or a request to delete something

**contact@easybyte.es**. If you want your installation's reports removed, send the identifier from
`hullwork config --telemetry` and they will be deleted.

The published image started reporting on **2026-08-06**. Before that it reported nothing, and the FAQ
